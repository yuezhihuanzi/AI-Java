> **阅读指南**  
> 泛型有两个绕不开的话题。一个是通配符：`List<?>`、`? extends T`、`? super T`分别能接收什么样的集合，边界很容易记混；另一个是类型擦除——泛型信息在编译后会被抹掉，很多"为什么这样不行"的怪象都源于此。把这两点弄清，泛型才算真正掌握。

## 3.1 通配符的引入

先看一个问题。假设有一个打印列表的方法：

```java
public void printList(List<Object> list) {
    for (Object obj : list) {
        System.out.println(obj);
    }
}
```

这个方法接受`List<Object>`。如果我传入`List<String>`，会发生什么？

```java
List<String> strings = Arrays.asList("a", "b", "c");
printList(strings); // ❌ 编译错误！
```

`String`是`Object`的子类，但`List<String>`<font color="red">**不是**</font>`List<Object>`的子类。泛型类型参数不支持继承关系的自动转换。这是为了保证类型安全——如果允许转换，就可能往`List<String>`里放入非String对象。

<font color="red">**通配符**</font>（`?`）就是为了解决这个问题的。

## 3.2 无界通配符

`?`表示未知类型，可以匹配任何类型：

```java
public void printList(List<?> list) {
    for (Object obj : list) {
        System.out.println(obj);
    }
}

List<String> strings = Arrays.asList("a", "b");
List<Integer> nums = Arrays.asList(1, 2);
printList(strings); // ✓ 可以
printList(nums);    // ✓ 可以
```

无界通配符适用于只读场景：你能从列表中读取元素（作为Object），但不能向其中添加元素（除了null）。

## 3.3 上界通配符（extends）

`? extends T`表示未知类型是`T`或`T`的某个子类。这称为<font color="red">**上界通配符**</font>。

```java
// Animal及其子类
class Animal { void eat() {} }
class Dog extends Animal { void bark() {} }
class Cat extends Animal { void meow() {} }

public void printAnimals(List<? extends Animal> animals) {
    for (Animal a : animals) {
        a.eat(); // 可以调用Animal的方法
    }
}

List<Dog> dogs = new ArrayList<>();
dogs.add(new Dog());
printAnimals(dogs); // ✓ List<Dog> 匹配 ? extends Animal
```

上界通配符的核心规则：<font color="red">**只读不写**</font>。

```java
public void addAnimal(List<? extends Animal> animals) {
    animals.add(new Dog()); // ❌ 编译错误！
}
```

为什么不能添加？因为编译器只知道列表中的元素是"某种Animal的子类"，但不知道具体是哪种。如果列表实际上是`List<Cat>`，放入`Dog`就破坏了类型安全。所以编译器选择保守策略：禁止一切写入（null除外）。

## 3.4 下界通配符（super）

`? super T`表示未知类型是`T`或`T`的某个父类。这称为<font color="red">**下界通配符**</font>。

```java
public void addAnimals(List<? super Dog> animals) {
    animals.add(new Dog());    // ✓ 可以
    animals.add(new Animal()); // ❌ 编译错误！
}
```

下界通配符的规则与上界相反：<font color="red">**只写不读**</font>（或者说读取时只能得到Object）。

```java
public void process(List<? super Dog> animals) {
    animals.add(new Dog());        // ✓ 安全
    Object obj = animals.get(0);   // 只能当Object读取
    Dog d = animals.get(0);        // ❌ 编译错误
}
```

原因：列表可能是`List<Dog>`、`List<Animal>`或`List<Object>`。所以放入`Dog`（或其子类）是安全的，但取出的元素类型无法确定——编译器只能保证它是Object。

## 3.5 PECS原则

<font color="red">**PECS**</font>（Producer Extends, Consumer Super）是Java泛型的经典口诀：

```
    ┌──────────────────────────────────────────┐
    │              PECS 原则                     │
    ├──────────────────────────────────────────┤
    │ Producer → extends（生产者用上界）          │
    │   如果要从集合中"取出"数据                   │
    │   使用 ? extends T                         │
    │                                          │
    │ Consumer → super（消费者用下界）            │
    │   如果要往集合中"放入"数据                   │
    │   使用 ? super T                           │
    └──────────────────────────────────────────┘
```

```java
// 生产者：从集合中读取
public double sum(List<? extends Number> numbers) {
    double total = 0;
    for (Number n : numbers) { // 读取
        total += n.doubleValue();
    }
    return total;
}

// 消费者：向集合中写入
public void addNumbers(List<? super Integer> list) {
    list.add(1);  // 写入
    list.add(2);
}
```

## 3.6 多重限定

类型参数可以有多个上界，使用`&`连接：

```java
public class MultiBound<T extends Comparable<T> & Serializable> {
    private T data;
    
    public void setData(T data) {
        this.data = data; // T必须同时实现Comparable和Serializable
    }
}
```

注意：如果上界中包含类，类必须写在第一个位置。

```java
// ✓ 正确：类在前
<T extends Animal & Serializable>

// ❌ 错误：类不在第一个位置
<T extends Serializable & Animal>
```

## 3.7 什么是类型擦除

本节配套视频请到 [原文](https://www.logamee.com/course-learning/77/1546) 观看。

Java的泛型是<font color="red">**伪泛型**</font>。与C++等语言的模板不同，Java泛型的类型参数仅在编译期存在。编译完成后，所有的类型参数都会被替换为其上界（默认是Object），这个过程称为<font color="red">**类型擦除**</font>（Type Erasure）。

```java
// 源码
public class Box<T> {
    private T value;
    public void set(T v) { this.value = v; }
    public T get() { return value; }
}

// 擦除后（编译器实际生成的字节码）
public class Box {
    private Object value;
    public void set(Object v) { this.value = v; }
    public Object get() { return value; }
}
```

这意味着运行时JVM根本不知道泛型参数的存在。`List<String>`和`List<Integer>`在运行时是同一个类。

```java
List<String> stringList = new ArrayList<>();
List<Integer> intList = new ArrayList<>();

System.out.println(stringList.getClass() == intList.getClass());
// 输出: true
```

## 3.8 擦除的规则

类型擦除遵循以下规则：

1. 如果类型参数有上界，替换为上界
2. 如果没有上界，替换为Object

```java
// T没有上界，擦除为Object
class Container<T> { T data; }
// 擦除后
class Container { Object data; }

// T有上界，擦除为上界
class NumberBox<T extends Number> { T value; }
// 擦除后
class NumberBox { Number value; }

// 多重限定，擦除为第一个上界
class MultiBound<T extends Comparable<T> & Serializable> { T data; }
// 擦除后
class MultiBound { Comparable data; }
```

## 3.9 擦除带来的限制

### 限制一：无法创建泛型数组

```java
T[] array = new T[10]; // ❌ 编译错误
```

因为运行时T被擦除为Object，无法确定数组的实际类型。

### 限制二：泛型类的静态上下文不能使用类型参数

```java
public class Box<T> {
    private static T staticField; // ❌ 编译错误
    private static void staticMethod(T t) {} // ❌ 编译错误
}
```

静态成员属于类本身，不属于某个具体实例。而泛型参数只有在实例化时才能确定，静态上下文无法获取类型信息。

### 限制三：instanceof不能检查泛型类型

```java
List<String> list = new ArrayList<>();
if (list instanceof List<String>) {} // ❌ 编译错误
if (list instanceof List) {}         // ✓ 可以使用原始类型
```

运行时`List<String>`和`List<Integer>`是同一个类，无法区分。

### 限制四：不能捕获泛型类型的异常

```java
public <T extends Throwable> void doWork() {
    try {
        // ...
    } catch (T e) {} // ❌ 编译错误
}
```

但可以在throws子句中使用类型参数。

## 3.10 桥接方法

类型擦除还带来一个有趣的现象：编译器会自动生成<font color="red">**桥接方法**</font>（Bridge Method）。

```java
class Node<T> {
    T data;
    void setData(T data) { this.data = data; }
}

class StringNode extends Node<String> {
    @Override
    void setData(String data) { super.setData(data); }
}
```

擦除后，父类`Node`的`setData`方法变为`setData(Object)`，而子类`StringNode`的`setData`是`setData(String)`。两个方法签名不同，从多态角度看子类的重写会失效。

编译器自动在`StringNode`中生成一个桥接方法：

```java
// 编译器自动生成
void setData(Object data) {
    setData((String) data); // 转换后调用真正的方法
}
```

这样多态机制就能正常工作。

## 3.11 擦除的设计原因

Java选择类型擦除而非具体化泛型（reified generics），主要是为了向后兼容。Java 5引入泛型时，已经有大量使用原始类型的代码。擦除机制确保了新老代码可以无缝混合使用。

```
    兼容设计
    ┌──────────────┐    ┌──────────────┐
    │   老代码      │◄──►│   新代码      │
    │  List list   │    │ List<String> │
    └──────────────┘    └──────────────┘
         │                     │
         └─────────────────────┘
              运行时完全兼容
```
