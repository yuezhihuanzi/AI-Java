## 4.1 包装类型的定义

Java 为 8 种基本类型提供了对应的<font color="blue">包装类型</font>（Wrapper Classes），它们将基本类型封装成对象，使其具有对象的相关特性：

| 基本类型 | 包装类型 |
|---------|---------|
| `byte` | `Byte` |
| `short` | `Short` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |
| `char` | `Character` |
| `boolean` | `Boolean` |

你可以这么理解，Java 为每一个基本类型又提供了另外一个「引用类型」的版本。以 `int` 整型为例，`int` 是一个基本类型，但还有一个类：`Integer`，也可以用来表示整数。

所以当我们创建一个整数时，你可以使用 `int`，也可以使用 `Integer`：

```java
int a = 10;
// 会有警告，该写法已在 Java9 中被废弃，且可能在未来版本移除
Integer b = new Integer(10); 
```

上述代码在 Java 中是可以执行的，第 1 行定义了 1 个基本类型；第 2 行实例化了 1 个整数对象。但第 2 行 Java 开发工具会有一个警告。

正确的创建整数对象的方法应该是下面这样：

```java
Integer b = 10;
```

这些很奇怪，但这确实是 Java 建议的写法。它用了基本类型的定义方式：直接赋值，但也实例化了一个 `Integer` 对象。

```java
Integer b = new Integer(10); 
Integer c = 10;
```

以上两种写法基本等价，之所以出现第 2 种写法是因为它写起来比第 1 种要简单。但为什么 Java 可以支持第 2 种写法？这其实是 Java 做的一点小魔术：

```java
// 当 Java 编译器遇到这段代码时会
// 将其转化为 Integer.valueOf(10)
// 它等同于 new Integer(10)
Integer c = 10;
```

我们可以不需要关注上述的详细的过程，`Integer.valueOf(10)` 超出了我们现在的知识范畴，随着学习的深入后面会逐步了解。我们只需要知道，可以使用字面量的方式直接创建出一个 `Integer` 对象。

这种写法将 1 个基本类型整数 10 转化成了它对应的包装类型（`int` → `Integer`），在 Java 中我们将这个过程称为「<font color="blue">**自动装箱**</font>」。

## 4.2 自动装箱与拆箱

再看一段代码：

```java
Integer a = 10;    
int b = a; 
```

第 1 行用自动装箱的方式创建了一个 `Integer` 包装类型 `a`，第 2 行将 `a` 又赋值给了基本类型 `b`。这样写可以吗？完全可以：

```java
// 自动装箱：基本类型 → 包装类型
Integer a = 10;    // 编译器转换为：Integer.valueOf(10)

// 自动拆箱：包装类型 → 基本类型
int b = a;         // 编译器转换为：a.intValue()
```

实际上当 1 个包装类型被赋值给基本类型时，编译器也会有一个小魔法，即调用 `a.intValue()` 进行自动的转换，将包装类型 `a` 又转回了基本类型 `b`。

同「自动装箱」相反，包装类型 → 基本类型的过程被称为「<font color="blue">**自动拆箱**</font>」。同学们目前可以暂时不去了解是怎么拆箱和装箱的，只需要知道这是由编译器完成自动完成的即可。

「自动装箱」和「自动拆箱」的关键点在于「自动」两个字，因为这个过程是由编译器自动完成的，无需我们手动编写。这实际上是为了简化代码，让我们可以更高效的完成编码。

如果你想手动完成「装箱」和「拆箱」也可以，其实就是调用上述代码中注释部分的 `Integer.valueOf()` 和 `a.intValue()`。

## 4.3 基本类型 VS 包装类型

我们这个小节来探讨下，既然有了简单的基本类型为什么还需要有对应的包装类型？

一个最简单的原因是，基本类型纯粹只为了表达现实世界里的数值，没有额外的附加能力。但包装类型不一样，包装类型是类，我们都知道类下面可以包含方法，这就为处理数值提供了非常丰富的手段。

基本类型的优势在于计算机处理速度快，性能好；缺点在于功能简单（几乎没有啥功能），没有办法参与到面向对象体系中（本身就不是类与对象，肯定就谈不上面向对象）。但包装类型则正好相反，它们相互弥补对方的缺陷。

举个例子，如果我有一个字符串 `"1024"`，但现在需要的是数字（整数）1024，如果有包装类型就很好处理，因为 `Integer` 类上有相关处理方法：

```java
int num = Integer.parseInt("1024"); // String → int
```

再比如，将 10 进制的数转换成 16 进制：

```java
String hex = Integer.toHexString(255); // 将 255，转换为 16 进制字符串："ff"
```

这些常见的功能都可以依靠 `Integer` 这个类下面的相关方法来实现。

还可以举一个例子包装类型的用处。包装类型属于对象，所以它可以有空值：`null`。以人的年龄为例，年龄通常为整数 0~N，但有时候某个人的年龄我们可能不知道是多少岁，那么怎么表达这个「不知道多少岁」？

基本类型 `int` 很难表达，比如用 0 表达合适吗？不太合适。但可以用包装类型对应的空值来表达：

```java
Integer age = null;
```

包装类还可以支持诸如泛型、集合等基本类型不能支持的能力。限于篇幅这里就不再一一举例。

包装类型优势这么多，是不是应该无脑选择包装类型？恰恰相反，<font color="red">**如非必要应该优先选择基本类型**</font>，因为基本类型性能最好，仅当基本类型无法胜任编码或者选择基本类型会让代码很复杂的时候才选择包装类型。

尤其要注意上小节我们探讨的自动装箱和自动拆箱，虽然这个机制很方便，但我们一定要避免频繁的「装箱」和「拆箱」，因为这个过程本身也比较消耗计算机的性能。尤其是进行大量循环的时候，非常容易频繁的自动装箱：

```java
// 这是段 Java 的循环
// 表示重复做某件事 1000000 次
// 比较低效代码，需要频繁的装箱
Long sum = 0L;
for (long i = 0; i < 1000000; i++) {
    sum += i; // 等价于 sum = Long.valueOf(sum.longValue() + i);
}

// 优化方案（减少装箱）
long primitiveSum = 0L; // 使用基本类型
for (long i = 0; i < 1000000; i++) {
    primitiveSum += i;
}
```

## 4.4 包装类型的缓存机制

Java 包装类型的缓存机制是为优化高频使用的小数值对象设计的重要性能优化策略，其核心逻辑是通过预创建常用的数值对象减少内存分配和垃圾回收开销，以提高程序运行效率。

### 什么是缓存机制？

包装类型属于对象（引用类型），每次创建新的对象对于计算机性能的消耗比较大。而常见基本类型的数值又具备「二八原则」，即 80%~90% 的场景都会使用一定范围内的数值，所以 Java 会将一些常用的数值（比如 -128 ~ 127 这样的数字）缓存起来，让每个包装类型都可以复用这些数字，从而避免重复创建对象。

下表展示了所有包装类型的缓存数值范围：

| 包装类型 | 缓存范围 | 内存节省原理 | 是否可配置 |
|---------|---------|-------------|-----------|
| `Integer` | -128 ~ 127 | 覆盖 90% 的整数使用场景 | 可通过 `-Djava.lang.Integer.IntegerCache` 扩展整数缓存范围 |
| `Long` | -128 ~ 127 | 常用小整数 | 不可配置 |
| `Short` | -128 ~ 127 | 覆盖全部 short 范围 | 不可配置 |
| `Byte` | -128 ~ 127 | 覆盖全部 byte 可能值 | 不可配置 |
| `Character` | `\u0000` ~ `\u007F` | ASCII 字符集 (0-127) | 不可配置 |
| `Boolean` | true/false | 只有两种可能值 | 不可配置 |
| `Float` | 无缓存 | 浮点数离散值无限 | - |
| `Double` | 无缓存 | 浮点数离散值无限 | - |

> **提示**  
> 统计显示：95% 的整数操作集中在 [-128, 127] 范围内。所以 Java 设置的缓存范围覆盖了绝大多数使用场景。

但这里要注意，只有通过 `Integer.valueOf()` 方法创建的对象才会应用缓存：

```java
Integer i = new Integer(10);      // 没有使用缓存，new 强制生成新对象
Integer i1 = Integer.valueOf(10); // 通过 Integer.valueOf()会使用整数缓存
```

> **最佳实践**  
> 优先使用 `valueOf()`，而非 `new Integer()` 来创建对象。

看一个具体示例：

```java
// 没有缓存时（每次 new 消耗约 12-24 字节）
for(int i=0; i<1000; i++) {
    list.add(new Integer(10)); // 创建 1000 个独立对象
}

// 有缓存后
for(int i=0; i<1000; i++) {
    list.add(Integer.valueOf(10)); // 所有元素指向同一个缓存对象
}
```

### 缓存机制的经典陷阱

由于缓存机制的存在，我们要特别注意一些经典的「陷阱」：

```java
Integer x = 128;
Integer y = 128;
boolean isEqual = x == y; // 请问，是否相等

Integer m = 127;
Integer n = 127;
boolean isEqual1 = m == n;  // 请问，是否相等
```

这是一个非常经典的 Java 面试题，考察的就是程序员对整数缓存的理解。正确答案是：第 3 行为 <font color="orange">`false`，不相等</font>；第 7 行为 <font color="orange">`true`，相等</font>。

首先分析下第 7 行为什么是相等，因为 127 位于整数的缓存范围内，实际上 `m` 和 `n` 都复用的同一个对象，而 `==` 符号比较的是对象的引用，`m` 和 `n` 都指向同一个对象，所以它们相等。

再来看第 3 行为什么不相等。因为 128 超出了缓存范围，实际上 `x` 和 `y` 通过装箱操作成为了两个不同的对象，那么 `x` 和 `y` 指向不同的地址，自然是不相等。

但很明显，第 3 行的结果不是我们想看到的，两个数值都是 128 凭啥判断为不相等？

可以用我们之前提到的 `equals()` 来判等：

```java
boolean isEqual = x.equals(y); // true
```

`equals()` 比较的是内容，而不是对象引用，`x` 和 `y` 内容相等，所以结果为 `true`。
