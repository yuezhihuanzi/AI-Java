## 5.1 为什么需要接口

想象一个现实世界的场景：有很多设备都支持"读写"功能，比如U盘。通常我们会将U盘插在电脑的USB接口上来读取或写入数据。但有没有考虑过，为什么一台电脑可以插入不同厂商生产的U盘？

这些U盘由于来自不同的厂商，内部实现(怎么读、怎么写)完全不同，那么电脑是如何实现对不同厂商U盘的读写的？

一种方案是，电脑根据不同的厂商定制不同的方案来进行读取。那么理论上如果生产U盘的厂家有1000家，电脑需要支持1000种方案。这太不合理了。

另一种方案(也是现在通用的方案):电脑只支持一个USB读写标准，所有U盘生产商都必须支持这个标准，不支持的无法读写。

Java里的`interface`(接口)类似于上述的方案2。接口可以规定一个方法签名，但不包含方法的实现。任何类都可以实现这个`interface`,只要实现了这个`interface`的类都具备该能力。

## 5.2 接口的定义

类似于类独占一个Java文件，`interface`也是一样，需要单独一个文件：

```java
// 定义一个名为SimpleInterface的接口
interface SimpleInterface {
    // 接口中可以声明多个接口方法
    // 接口中的方法类似抽象方法,没有实现,只有签名
    void doSomething();
    void doOtherThing();
    // 可以有返回值,也可以有参数
    int calculator(int x, int y);
}
```

在Java 8之前，接口中的所有方法都默认是`public abstract`的抽象方法(没有实现，只有签名)。所以这些关键字可以省略掉：

```java
interface Readable {
    // 以下两种定义方式完全等价
    public abstract int read(byte[] buffer);
    void close(); // 自动是public abstract
}
```

接口除了声明抽象方法，还可以声明静态变量：

```java
interface USB {
    // 以下两种定义方式完全等价
    public static final double VERSION = 3.0;
    String PROTOCOL = "USB"; // 自动是public static final
}
```

接口中的所有字段都默认是`public static final`的，即公共的、静态的常量。

## 5.3 实现interface

类可以用关键字`implements`实现一个或多个接口。实现接口的类必须遵守以下规则：

- 它必须为接口中所有的抽象方法提供具体实现
- 它可以选择使用接口中提供的默认方法，也可以重写它们

```java
interface Readable {
    public int read(byte[] buffer);
}

interface Writable {
    int write(byte[] data);
}

// 一个类可以实现多个接口
class HardDisk implements Readable, Writable {

    // 必须实现Readable的抽象方法
    @Override
    public int read(byte[] buffer) {
        System.out.println("Reading data from HardDisk...");
        return buffer.length;
    }

    // 必须实现Writable的抽象方法
    @Override
    public void write(byte[] data) {
        System.out.println("Writing data to HardDisk...");
    }
}
```

## 5.4 接口的使用与多态

你其实可以把`interface`看做是一个类的父类(仅限于在使用方式上很像)。

```java
// 定义接口
public interface Animal {
    void makeSound();
}

// 实现接口
public class Dog implements Animal {
    private String name;

    public Dog(String name) {
        this.name = name;
    }

    @Override
    public void makeSound() {
        System.out.println(name + "说: 汪汪!");
    }

    // 自有方法
    public void breathe() {
        System.out.println("呼吸空气中...");
    }
}

// 使用接口
public class Main {
    public static void main(String[] args) {
        // 使用接口类型声明变量
        Animal myDog = new Dog("Buddy");
        myDog.makeSound(); // 输出: Buddy说: 汪汪!
    }
}
```

最核心的代码是`Animal myDog = new Dog("Buddy")`。`new Dog()`却赋值给了`Animal`类型。是的，接口也可以作为一个类型。这其实也是一种"多态":

```java
Animal myDog = new Dog("Buddy");
Animal myCat = new Cat("ShanKui");
Animal myBird = new Bird("QiuQiu");
```

思考一下，请问下面的代码可以调用吗：

```java
Animal myDog = new Dog("Buddy");
myDog.breathe();
```

仔细回顾下之前讨论的向上转型，就知道这里`breathe()`是不可能调用的。因为向上转型的类型`Animal`根本没有`breathe()`方法。

## 5.5 抽象类和接口的区别

| 特性       | 接口(Interface)                          | 抽象类(Abstract Class)                     |
| ---------- | ---------------------------------------- | ------------------------------------------ |
| 方法       | 主要是抽象方法(Java 8+有默认和静态方法)  | 抽象方法和具体方法都可以有                 |
| 字段       | 只能是`public static final`常量          | 可以是各种类型的实例变量和静态变量         |
| 构造函数   | 没有                                     | 有(虽然不能直接实例化)                     |
| 继承       | 一个类可实现多个接口                     | 一个类只能继承一个抽象类                   |
| 设计理念   | "具有某种能力"(has-a/can-do)定义行为契约 | "是一个"(is-a)定义对象的核心身份           |
| 访问修饰符 | 方法默认是`public`                       | 方法可以是`public`、`protected`、`private` |

<font color="red">**如何选择？**</font>

- 如果关注的是<font color="red">**共享行为**</font>(做什么),并且这些行为可能跨越毫不相关的类体系，请使用<font color="red">**接口**</font>。例如：`Flyable`(能飞)可被`Bird`和`Airplane`实现
- 如果关注的是<font color="red">**代码复用和定义一类对象的核心身份**</font>(是什么),请使用<font color="red">**抽象类**</font>。例如：`Animal`是`Dog`和`Cat`的核心父类

一个类可以"组合"多个接口，这其实是一个非常好的模式。现代Java设计更倾向于"组合优于继承"和"面向接口编程",以降低耦合度，提高灵活性。

> 如果类的继承和组合多个接口都可以实现某种业务，那么更推荐"组合多个接口"。组合>继承，这是现代Java更推荐的模式。

## 5.6 默认方法(Java 8+)

接口除了能够包含多个抽象方法，还可以包含"默认方法"。

为了解决接口演化问题(向已有接口添加新方法而不破坏所有现有实现类),Java 8引入了默认方法。

默认方法使用`default`关键字修饰，必须提供方法体。实现类可以继承它(不重写，类似类方法的继承),也可以重写它。

简单谈一下为什么需要"默认方法"。

在Java 8之前，接口里只有抽象方法：

```java
interface Readable {
    void read(byte[] buffer);
}
```

所有实现这个接口的类都必须将接口中的方法全部实现，不能选择性地实现。

假如有五个类A、B、C、D、E最开始实现了`Readable`接口，但后面因为业务变化，需要在`Readable`接口里新增一个方法：

```java
interface Readable {
    void read(byte[] buffer);
    void reset(); // 新增抽象方法
}
```

由于实现类必须实现接口的全部抽象方法，这就意味着必须为五个实现类全部新增一个`reset()`的实现。那假如有1000个类，岂不是要修改这1000个类？这其实违反了开闭原则。

Java 8为了解决这个问题，提供了新的机制——默认方法：

```java
interface Readable {
    int read(byte[] buffer); // 抽象方法

    // 默认方法,必须有方法体
    default void reset() {
        System.out.println("Reset is supported by default.");
    }
}
```

默认方法是有方法实现的，所以实现类只有在需要修改这个默认方法的时候才需要重写。这样既可以保证全部实现类都遵守"必须实现所有接口方法",同时又能避免在新增接口方法后所有实现类都要修改的问题。

```java
class HardDisk implements Readable {

    @Override
    public int read(byte[] buffer) {
        System.out.println("Reading data from HardDisk...");
        return buffer.length;
    }

    // 可以选择重写默认方法,也可以不重写
    @Override
    public void reset() {
        System.out.println("HardDisk is being reset.");
    }
}
```

## 5.7 静态接口方法(Java 8+)

类似于类的静态方法只属于类而不属于实例对象，接口中的静态方法属于接口本身，而不是实现类的对象。使用`static`关键字修饰，必须提供方法体。

可以通过`接口名.静态方法名()`的方式调用：

```java
interface USB {
    static String getSpecification() {
        return "Universal Serial Bus";
    }
}
// 调用:USB.getSpecification();
```

## 5.8 私有接口方法(Java 9+)

Java的接口在设计之初，本来的目的是为了给类定制必须遵守的契约。所以很自然地，所有的接口方法都应该是`public`的。

但一切随着Java 8而有所变化。Java 8新增了默认方法，有了默认方法，接口内部存在`private`的私有方法就有意义了。

最核心的原因是，默认方法可以包含方法体，既然可以在`interface`内部编写具体方法了，那么就存在代码共用的问题。

```java
interface Animal {
    void performAction();

    // 默认方法:模拟行走
    default void walk() {
        System.out.println("调整身体平衡");
        System.out.println("检查周围环境");
        System.out.println("准备移动");
        System.out.println("用四肢交替移动");
        System.out.println("放松肌肉");
        System.out.println("记录移动距离");
    }

    // 默认方法:模拟奔跑
    default void run() {
        System.out.println("调整身体平衡");      // 与walk方法重复
        System.out.println("检查周围环境");      // 重复
        System.out.println("准备移动");          // 重复
        System.out.println("快速交替四肢移动");
        System.out.println("放松肌肉");          // 重复
        System.out.println("记录移动距离");      // 重复
    }
}
```

仔细观察，两个默认方法中有很多重复的代码。聪明的我们会想到，可以将这些重复的代码提取出来成为一个公共的方法：

```java
interface Animal {
    void performAction();

    default void walk() {
        prepare();
        System.out.println("用四肢交替移动");
        cleanupAfterMovement();
    }

    default void run() {
        prepare();
        System.out.println("快速交替四肢移动");
        cleanupAfterMovement();
    }

    // 公共方法:活动前的准备工作
    default void prepare() {
        System.out.println("调整身体平衡");
        System.out.println("检查周围环境");
        System.out.println("准备移动");
    }

    default void cleanupAfterMovement() {
        System.out.println("放松肌肉");
        System.out.println("记录移动距离");
    }
}
```

语法没问题，但不符合封装性。

类需要遵循封装性，接口也需遵守——不必要的就不要公开给其他类。上述案例的`prepare()`和`cleanupAfterMovement()`方法其实是为了接口内部共享的代码，它们是内部的细节，不应该暴露给外部。但问题是，它们被设置成了`default`默认方法，是公开的。

Java 9提出的私有方法，解决了这个问题：

```java
interface Animal {
    void performAction();

    // 私有方法:仅接口内部使用
    private void prepare() {
        // ....
    }

    private void cleanupAfterMovement() {
        // ....
    }
}
```

将`default`替换成`private`即可。

## 5.9 接口的继承

同类的体系一样，接口也有继承体系，且<font color="red">**接口可以多重继承**</font>(一个接口可以继承多个父接口)。这是Java中实现多重继承的唯一方式。

```java
interface A {
    void methodA();
}

interface B {
    void methodB();
}

// 接口C同时继承了接口A和B
interface C extends A, B {
    void methodC();
}

// 实现接口C的类必须实现methodA、methodB、methodC
class MyClass implements C {
    @Override
    public void methodA() { /* ... */ }

    @Override
    public void methodB() { /* ... */ }

    @Override
    public void methodC() { /* ... */ }
}
```

## 5.10 面向对象编程的核心思想是类与类的交互

面向对象编程(OOP)的核心思想之一就是让不同的"类"各司其职，并通过"交互"(即互相调用方法)来共同完成复杂的任务。

用一个生活化的例子来解释：一个简单的"外卖订单系统"。在这个系统里，主要有两个"类":

- `Customer`(顾客类)
- `Restaurant`(餐厅类)

它们之间会发生一次典型的"交换":顾客下单，餐厅处理订单。

```java
// Customer.java
public class Customer {
    private String name;
    private String address;

    public Customer(String name, String address) {
        this.name = name;
        this.address = address;
    }

    // 最重要的行为:下单!
    public void placeOrder(Restaurant restaurant, String dishName) {
        System.out.println(this.name + " 正在向 " + restaurant.getName() + " 下单一份 " + dishName);

        // 这里是"交换"的关键!
        // 顾客对象"调用"了餐厅对象的"处理订单"方法
        String message = restaurant.processOrder(dishName, this.address);
        System.out.println(message);
    }

    public String getName() {
        return name;
    }
}

// Restaurant.java
public class Restaurant {
    private String name;

    public Restaurant(String name) {
        this.name = name;
    }

    public String processOrder(String dishName, String deliveryAddress) {
        System.out.println(this.name + " 餐厅已收到订单:制作一份 " + dishName);
        System.out.println("即将配送到:" + deliveryAddress);

        try {
            Thread.sleep(2000); // 模拟烹饪时间
        } catch (InterruptedException e) {
            e.printStackTrace();
        }

        return "【订单完成】" + dishName + " 已由 " + this.name + " 制作完成,正在送往 " + deliveryAddress + "!";
    }

    public String getName() {
        return name;
    }
}
```

最核心的就是`placeOrder`方法，这充分体现了两个对象的交互，它们共同作用完成了"下单"这个业务。

整个程序运行的关键点就是三个类之间的交互：

- `Main`(负责启动和实例化类，并让类在这里交互)
- `Customer`(负责客户所有的行为和属性)
- `Restaurant`(负责餐厅所有的行为和属性)

真实的案例里，可能有上千个类，它们之间相互作用，共同完成整个程序。

## 5.11 耦合(Decoupling)

什么是耦合？

<font color="red">**耦合**</font>(Coupling):指一个软件模块(类、组件)与另一个模块之间的依赖程度。紧耦合(High Coupling)意味着一个模块的改动很可能导致另一个模块也必须改动，代码难以维护和扩展。

软件开发的最核心目标是在保证程序正确稳定运行的前提下，应尽可能地降低成本。而软件维护(修改、更新)的成本远远大于软件最早期的开发成本。程序耦合会大幅提升软件的维护成本。

> 耦合的程序在开发阶段成本比较低，因为你啥都不用考虑，就写写写，那自然很快就能写出来。但如果想要写出低耦合的程序，降低后期的维护成本，那前期开发时的成本就比较高，因为要考虑的问题比较多。

耦合像胶水一样让整个系统都牢牢地粘结在一起，这是非常不好的做法。我们期望的好的程序系统不应该是被胶水粘起来的，而更应该像是乐高，可插拔、可替换。

下面举一些常见的耦合代码，同学们可以尽量避免这样的写法。

### 内容耦合(最高耦合级别)

```java
// 模块A
class ModuleA {
    private String internalData = "秘密数据";

    // 暴露内部数据的方法(不应该这样做)
    public String getInternalData() {
        return internalData;
    }
}

// 模块B - 直接依赖ModuleA的内部实现
class ModuleB {
    public void process(ModuleA a) {
        // 直接访问和依赖ModuleA的内部数据
        String data = a.getInternalData();
        System.out.println("处理: " + data);
    }
}
```

模块B紧紧"咬着"模块A,直接依赖模块A的内部实现。假如模块A的`getInternalData()`方法发生了变化(比如删除了，或者返回类型从`String`改成了`int`),模块B就会出错。这是典型的违反开闭原则。

### 公共耦合

指多个模块共享相同的全局数据：

```java
// 全局共享数据
class GlobalData {
    public static int counter = 0; // 公共数据
}

// 模块A
class ModuleA {
    public void increment() {
        GlobalData.counter++; // 修改全局数据
    }
}

// 模块B
class ModuleB {
    public void display() {
        System.out.println("计数器: " + GlobalData.counter);
    }
}
```

模块A和模块B之间没有直接引用，但都和`GlobalData`耦合。一旦出现了问题，就很难知道到底是谁修改了`GlobalData`里的数据。

### 印记耦合(Stamp Coupling)

模块接收或传递不需要的数据结构：

```java
// 用户类包含许多字段
class User {
    private String name;
    private String email;
    private String address;
    private String phone;
    // ... 许多其他字段
}

// 邮件服务只需要email,但接收整个User对象
class EmailService {
    public void sendWelcomeEmail(User user) {
        // 只使用user的email字段,但接收了整个User对象
        String email = user.getEmail();
        System.out.println("发送欢迎邮件到: " + email);
    }
}
```

`EmailService`只需要邮件信息，但是却将整个`User`对象作为参数传入，这是不好的写法。

## 5.12 面向接口编程，而非实现

虽然解耦方案很多，但有一条是最核心、最基础的：

> <font color="red">**面向抽象编程，而非面向实现。**</font>

什么意思？

在模块与模块交互的时候，不要让A模块依赖具体的B模块，而是让A依赖于一些抽象的契约。A模块只需要知道B模块"能做什么",但不需要知道B模块到底"怎么做的"。

如果A模块依赖于B模块"具体"怎么做，那A就和B产生了强依赖。一旦B模块"具体"的实现方式变了，A就要跟着B一起修改。

但如果A不管你怎么做，只要你能做就行，A根本就不会依赖B具体怎么实现，那无论B怎么改变具体的实现，A都不需要修改。

面向抽象编程的具体实现就是：面向接口编程或者面向抽象类编程，但不要面向具体实现(类)来编程。

### 从"面向实现"到"面向接口"的演进

<font color="red">**阶段一：紧耦合的面向实现编程**</font>

```java
// 具体的Dog类
public class Dog {
    public void shout() {
        System.out.println("汪汪汪!");
    }
}

// 具体的Cat类
public class Cat {
    public void shout() {
        System.out.println("喵喵喵!");
    }
}

// 动物园类,直接依赖具体的Dog和Cat
public class Zoo {
    private Dog dog;
    private Cat cat;

    public Zoo() {
        this.dog = new Dog(); // 在内部直接创建(紧耦合)
        this.cat = new Cat(); // 在内部直接创建(紧耦合)
    }

    public void showAnimals() {
        dog.shout();
        cat.shout();
    }
}
```

存在问题：

- <font color="red">**僵化**</font>:严重依赖具体类，新增`Tiger`必须修改`Zoo`类
- <font color="red">**脆弱**</font>:如果`Dog`的`shout()`方法改名，`Zoo`类也必须跟着修改
- <font color="red">**难以测试**</font>:无法用模拟的动物来替代测试

<font color="red">**阶段二：引入接口，但依赖获取方式未变**</font>

```java
public interface Animal {
    void shout();
}

public class Dog implements Animal {
    @Override
    public void shout() {
        System.out.println("汪汪汪!");
    }
}

public class Cat implements Animal {
    @Override
    public void shout() {
        System.out.println("喵喵喵!");
    }
}

public class Zoo {
    private Animal animal1; // 进步:声明为接口类型
    private Animal animal2; // 进步:声明为接口类型

    public Zoo() {
        this.animal1 = new Dog(); // 问题:仍然在内部创建具体对象
        this.animal2 = new Cat(); // 问题:仍然在内部创建具体对象
    }

    public void showAnimals() {
        animal1.shout();
        animal2.shout();
    }
}
```

进步在于成员变量现在是`Animal`接口类型，但`Zoo`仍然在自己创建具体的动物对象。耦合度依然很高。

<font color="red">**阶段三：真正的面向接口编程(依赖接口 + 依赖注入)**</font>

```java
// 接口和实现类保持不变
public interface Animal {
    void shout();
}

public class Dog implements Animal {
    @Override
    public void shout() {
        System.out.println("汪汪汪!");
    }
}

public class Cat implements Animal {
    @Override
    public void shout() {
        System.out.println("喵喵喵!");
    }
}

// 甚至可以轻松加入新的动物
public class Tiger implements Animal {
    @Override
    public void shout() {
        System.out.println("嗷呜~!");
    }
}

// 彻底改革的Zoo类
public class Zoo {
    // Zoo只依赖于Animal接口的列表,完全不知道也不关心具体有哪些动物
    private List<Animal> animals;

    // 依赖的AnimalList通过构造函数注入。Zoo自己不再创建任何Animal!
    public Zoo(List<Animal> animals) {
        this.animals = animals;
    }

    public void showAnimals() {
        for (Animal animal : animals) {
            animal.shout(); // 多态的魅力
        }
    }
}

public class Main {
    public static void main(String[] args) {
        // 1. 在程序的最外层(组装层)创建所有具体对象
        List<Animal> animalList = new ArrayList<>();
        animalList.add(new Dog());
        animalList.add(new Cat());
        animalList.add(new Tiger()); // 新增Tiger,但Zoo类完全无需任何改动!

        // 2. 将创建好的对象"注入"到Zoo中
        Zoo zoo = new Zoo(animalList);

        // 3. 使用Zoo
        zoo.showAnimals();
    }
}
```

上述代码核心是：<font color="red">**谁使用，谁不创建；谁创建，谁注入**</font>。

要使用动物类的是`Zoo`类，但它不负责创建，而是由`Main`类负责创建具体的动物。谁创建的动物谁负责将它们"注入"到`Zoo`类中。这种注入过程，有时候我们也称之为"<font color="red">**依赖注入**</font>"。上述的注入称之为"构造函数注入"。

> 看一个类有没有依赖实现，可以看它内部有没有`new`,一旦有`new`的代码，多半这个类就是依赖了实现，而不是依赖抽象。

### 无法完全消除实现，只能"隔离"实现

阶段三的代码中，在`Main`类中不也有类似于阶段二的问题吗：

```java
animalList.add(new Dog()); // 问题:依赖了实现
animalList.add(new Cat()); // 问题:依赖了实现
animalList.add(new Tiger()); // 新增也要加
```

看起来阶段三好像玩了个"文字游戏",将依赖实现的代码从`Zoo`类中，转移到了`Main`类中。这有意义吗？

非常有意义。

依赖实现的代码是无法完全消除的，只能将这些代码集中隔离在某一个类或者某个模块中。`new Dog()`、`new Cat()`这样的实例化都不可能消除掉，必须有类负责去实例化这些具体的对象。

我们可以将依赖实现的代码都集中在某个类或者模块中，让这些模块来管理依赖。这样做的好处是，将所有不稳定的代码都集中起来管理。

有很多第三方的库或者组件，专门是用来管理这些不稳定代码的，比如<font color="red">**Spring**</font>。它提供了容器(通常称为IOC容器),专门用来隔离所有变化的、不稳定的、依赖实现的代码。这相当于我们自己程序中就没有依赖实现的代码了。

现在的Java项目中，依赖注入大部分都会采用Spring容器。当我们需要使用接口(`Animal`)时，不需要自己去实例化，而是问"容器"去要这些`Animal`,容器负责创建后再注入到我们的`Zoo`类中。

<font color="red">**一句话概括**</font>:面向接口编程就是让"调用者"(如`Zoo`)和"被调用者"(如`Dog`)互相不知道对方的存在，它们都只和一个共同的"契约"(`Animal`接口)打交道。
