## 6.1 多态到底神奇在哪里

<font color="red">**问**</font>：老师，多态不就是父类引用指向子类对象吗？感觉也没什么特别的。

<font color="red">**答**</font>：你说的"父类引用指向子类对象"只是语法表象，不是本质。

<font color="red">**问**</font>：那本质是什么？

<font color="red">**答**</font>：多态的本质是<font color="red">**同一份代码，根据实际类型的不同，执行不同的逻辑**</font>。

```java
void handleAnimal(Animal animal) {
    animal.speak();  // 这一行代码
}

handleAnimal(new Cat());  // 打印"喵喵"
handleAnimal(new Dog());  // 打印"汪汪"
```

<font color="red">**问**</font>：如果不用多态，怎么写？

<font color="red">**答**</font>：

```java
void handleAnimal(Animal animal) {
    if (animal instanceof Cat) {
        ((Cat) animal).speak();
    } else if (animal instanceof Dog) {
        ((Dog) animal).speak();
    }
    // 每加一种动物,就要改一次这个方法
}
```

<font color="red">**问**</font>：区别在于，多态让这个方法不用改？

<font color="red">**答**</font>：对。这就是开闭原则——新增动物类型时，`handleAnimal`方法完全不用动。没有多态，每加一种动物就要改一次。

> 多态不是"能做什么",而是"不用做什么"。

<font color="red">**问**</font>：不用写if-else了？

<font color="red">**答**</font>：不用写了，而且永远不用写了。这就是多态真正的价值。

## 6.2 接口和抽象类到底选谁

<font color="red">**问**</font>：老师，接口和抽象类都有抽象方法，都能约束子类。什么时候该用谁？

<font color="red">**答**</font>：用一个例子回答你。假设你要设计一个"飞行器"体系。

<font color="red">**问**</font>：好，飞行器。

<font color="red">**答**</font>：先问一个问题：`Bird`(鸟)和`Airplane`(飞机),它们是什么关系？

<font color="red">**问**</font>：完全不同体系的东西，没有继承关系。

<font color="red">**答**</font>：但它们都有一个共同行为——"能飞"。这个"能飞"应该用什么定义？

<font color="red">**问**</font>：接口。因为鸟和飞机不是"is-a"的关系，不能用抽象类。

<font color="red">**答**</font>：对。那`Animal`体系呢？`Dog`和`Cat`之间呢？

<font color="red">**问**</font>：`Dog`和`Cat`都是动物的一种，用抽象类`Animal`作为父类。

<font color="red">**答**</font>：总结得很清楚。再看一个场景：如果`Bird`既要继承`Animal`,又要有"能飞"的能力呢？

<font color="red">**问**</font>：`Bird`继承`Animal`(is-a关系),同时实现`Flyable`接口(can-do能力)?

<font color="red">**答**</font>：完全正确。这就是两种抽象方式的组合使用：

```java
abstract class Animal { }

interface Flyable { void fly(); }

class Bird extends Animal implements Flyable { }
```

> 抽象类定义"是什么"(is-a),接口定义"能做什么"(can-do)。

<font color="red">**问**</font>：那一个类只能继承一个抽象类，但能实现多个接口——这不是接口的优势？

<font color="red">**答**</font>：是优势，也是Java设计者刻意为之。因为类的多重继承会导致菱形问题，而接口的多重实现不会。

## 6.3 依赖注入是不是只是文字游戏

<font color="red">**问**</font>：老师，阶段三把`new Dog()`从`Zoo`移到了`Main`,不就是换了个地方`new`吗？有什么区别？

<font color="red">**答**</font>：区别在于，<font color="red">**不稳定的代码被集中管理了**</font>。

```java
// 阶段二:不稳定的代码散落在Zoo内部
class Zoo {
    public Zoo() {
        this.dog = new Dog();  // Zoo依赖了Dog的具体实现
    }
}

// 阶段三:不稳定的代码集中在Main里
class Zoo {
    public Zoo(List<Animal> animals) {
        this.animals = animals;  // Zoo不知道也不关心有哪些动物
    }
}
```

<font color="red">**问**</font>：但如果业务变了，还是要改Main里的代码？

<font color="red">**答**</font>：对，但Main只负责组装，它是整个系统最不稳定的地方。在实际项目中，连Main都不需要自己写——Spring容器负责做这件事。

<font color="red">**问**</font>：也就是说，Spring帮我们把所有`new`的代码都接管了？

<font color="red">**答**</font>：差不多。你把对象创建交给Spring,自己只管业务逻辑。`Zoo`类里看不到一个`new`,它就真正做到了面向接口编程。

<font color="red">**问**</font>：所以依赖注入的意义不在于"消除new",而在于"谁来new"?

<font color="red">**答**</font>：对。让专业的容器做专业的事，业务类只管契约和交互。
